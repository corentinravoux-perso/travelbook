# 0001. Export fidelity: vector or raster print PDF

Status: decided by Corentin on 2026-11-15 — **vector route, with photo adjustments baked into the export derivative** (see "Gate outcome" at the end). Spike date: 2026-11-14. Task 7.3 implements this route.

## Context

Design §10 offers a vector print PDF (Chromium `printToPDF`) if it keeps photo resolution and fonts, and falls back to
600 dpi page captures assembled with pdf-lib otherwise. The spike (`spikes/export-fidelity/`) renders one page of
216 x 303 mm (A4 + 3 mm bleed) in a hidden Electron 45.3.2 window (Chromium of that release, Linux, Wayland session,
software-composited, `--no-sandbox`). The page holds: a gradient background; a 2551 x 1700 JPEG in a rounded frame with box shadow;
a 1800 x 1800 JPEG in an ellipse clip with `filter: saturate(1.3) contrast(1.1)`; a 1600 x 1200 JPEG at `opacity .8`,
rotated 7 degrees; an SVG sticker and a 600 x 600 PNG sticker with alpha, both rotated; two text blocks in two woff2
fonts (Playfair Display 700, Caveat 700; one with `text-shadow`). Photos are synthetic (gradients, fine detail, noise;
JPEG q92), generated by `gen-assets.mjs`; no personal photo. Poppler 'pdfimages / pdffonts / pdfinfo / pdftoppm' did the checks.

### 6. PDF versus capture (`node compare.mjs out/out-prefer-css.pdf out/out-300.png 300`; sharp, both resampled to the capture size)

`pdftoppm -r 300` gives 2550 x 3579 (page is 215.9 mm wide), capture 2551 x 3579. Mean absolute pixel difference

The residual includes the 1 px width mismatch and the 300 dpi shadow masks. Visually equivalent; not pixel exact.

## Decision

Rule (task brief): vector PDF route if measurements 1 to 4 hold; otherwise raster PDF route (600 dpi captures assembled with pdf-lib).

- 1 holds only at the tolerance edge (-0.100 mm width with `preferCSSPageSize: true`).
- 2 fails for the filtered photo (948 x 797, Flate, instead of 1800 x 1800 JPEG).
- 3 holds. 4 fails for one effect: CSS `filter`.

**Decision: raster PDF route** (600 dpi page captures assembled with pdf-lib; captures work: 5102 x 7157 in 6.6 s, about 2.2 GB peak across processes).

Effects that forced it: CSS `filter` (here `saturate()` + `contrast()`) on a photo. Nothing else did: clip-path, border-radius,
box-shadow, text-shadow, opacity, rotation, SVG and alpha PNG all kept photos as JPEG passthrough at source size.

### Recorded alternative (adjustments fail only: bake them into the derivative)

Only adjustments failed. The alternative the gate may prefer: keep the vector route and apply photo adjustments
(saturation, contrast, others) in the main-process `sharp` derivative (design §10 already produces a cropped, resized derivative per
photo), so export markup never uses CSS `filter`. The spike already shows the remaining page (clip, shadow, opacity, rotation, stickers,
embedded vector text) exports as vector with JPEG passthrough (`var-clip.pdf`: the 1800 x 1800 photo without `filter` is passed through).
Caveats if chosen: the baked adjustment must match the editor preview (`SpreadView quality="export"` must not apply the CSS
filter to the same photo), the page-size width must be fixed up with pdf-lib (-0.100 mm), shadows stay 300 dpi masks, and
this alternative has not been tested with a pdf-lib MediaBox rewrite or a baked derivative of the filtered photo.

## Gate outcome (2026-11-15)

Corentin chose the alternative: **vector PDF route with adjustments baked into the derivative.**

- Task 7.1 applies `adjust` (brightness, contrast, saturation, grayscale, sepia) to the export
  derivative with sharp. In `export` quality, `SpreadView` then draws the photo with no CSS
  `filter`, so `printToPDF` keeps it as a JPEG at the derivative's pixel size.
- The editor keeps the CSS `filter`. Task 7.1 adds a test comparing the sharp result with the
  CSS-filtered capture of the same photo (mean absolute difference under 2 %).
- Any other effect found later to rasterise falls back to the raster route for that page only.
- Page size: Chromium quantises the page to whole points (216 mm → 215.900 mm). This is
  inside the 0.1 mm tolerance and is absorbed by the 3 mm bleed.
- Captures need an offscreen window; `printToPDF` needs a plain hidden window (see above).
- Memory grows with page area; capture one page at a time.

Two combinations have no equivalent without a filter, so their page uses the **raster fallback**
(`export/rasterFallback.ts`): a photo with a shadow _and_ a feathered edge (the shadow follows the soft edge, which a shape
under the photo does not have), and a text with a shadow _and_ an outline but no fill. Such a page is captured at 600 dpi
(5102 x 7157 px for 216 x 303 mm), encoded as a q95 4:4:4 JPEG and embedded as one image by pdf-lib, crop marks and boxes
included; the other pages stay vector. The fixture's page 8 (feathered photo with a shadow) proves it: one `jpeg` of
5102 x 7157 on the page.

Known approximation: a photo whose file has transparency (PNG or WebP with alpha) shows the shadow shape through its
transparent parts, where the editor shows only the shadow outside it.

Fidelity: every page of the fixture is within 0.41 % mean absolute difference of the image-route export (`pdftoppm -r 300`
against the 300 dpi capture; the page 5 of the brief is 0.03 %). Fonts: `pdffonts` lists every font `emb yes`, `sub yes`.
Page size: Chromium prints 612 x 858.96 pt for a 216 x 303 mm box; the page is drawn at the top left of a page whose MediaBox
is the exact 612.283 x 858.898 pt, so the missing 0.1 mm is blank, inside the bleed.

Time (Linux, software-composited Electron): 0.33 s per vector page (derivatives, print, merge; text and photo pages),
13.4 s for a page sent to the raster fallback (two windows opened, a 600 dpi capture, JPEG encode). The 100-page time and peak
memory of the stress fixture are measured by Task 8.2.

## Crop marks start outside the bleed (Task 7.4)

Task 7.3 placed the marks 2 mm from the trim, inside the 3 mm bleed, where they overlay bleed artwork. A printer expects
marks that never touch printed content. The marks now start `markOffset` from the trim, the book's bleed (cover:
`coverBleed`), even when the export itself has no bleed, run 3 mm, and the MediaBox slug beyond the bleed box is
`markOffset + 3 mm + 1 mm` (`slugMm`). For the default 3 mm bleed the slug is 7 mm and an A4 page with marks is
**230 x 317 mm** (it was 228 x 315); BleedBox 216 x 303 at (7, 7), TrimBox 210 x 297 at (10, 10). The cover sheet has its own
slug, from `coverBleed`. Covered by `pdf.test.ts` (no mark point inside the bleed box) and `export-pdf.spec.ts` (dark mark
pixel at 5.5 mm, white slug beside it).

## A run is staged, then published; pages are spilled to disk (Phase 7 review fixes)

**Earlier exports are not touched until a run completes.** A run writes its files into a hidden folder of the output folder,
`.travelbook-export-<uuid>/` (`export/staging.ts`), and moves them out only after the last page (`publishStaged`: an earlier
file of the same name is first moved aside inside the staging folder, and if a move fails every earlier file is put back, so
a PDF open in a viewer cannot leave half old, half new). A cancel or a failure removes only the staging folder: the earlier
export stays as it was. The staging folders of runs that died (a crash, a kill) are removed at the start of the next run in
that folder. A file of an earlier export whose name the new run does not produce (page 4 of a 10-page export, re-exported as
3 pages) is left alone.

**The PDF route holds no page while it prints.** Each printed page, or each 600 dpi JPEG of the raster fallback, is written to
`<staging>/pages/` as soon as it exists; the merge (`assemblePdf` takes the pages from an async source) reads one back,
embeds it in the pdf-lib document, and drops it. The export windows are closed before the merge starts. pdf-lib keeps the
whole document and `save()` allocates the whole output, so the merge itself still needs about twice the size of the PDF in
memory (the document, then the saved bytes); a streaming writer would remove the second copy and is the next lever if Task
8.2 shows it matters.

Measured with a fake renderer in the main process (no Chromium: its windows come on top), 30 pages A4 + bleed with crop
marks, 28 vector pages of a 4.1 MB photo and 2 raster-fallback pages of a 23.3 MB JPEG (600 dpi, q95), a 161 MB PDF; peak RSS
(`VmHWM`), process at 279 MB before the run: whole run 910 MB before the fix, 814 MB after (the raster capture and its JPEG
encode account for most of the peak, about 535 MB for one page, and nothing is held while the next page prints any more);
merge phase 607-614 MB before, 585-587 MB after; 28 vector pages only (122 MB PDF): 511-515 MB before, 510 MB after.
